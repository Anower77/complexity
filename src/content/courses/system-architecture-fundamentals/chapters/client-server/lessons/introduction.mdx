## 1. The Core Paradigm

At the core of virtually every distributed system lies a simple separation of responsibilities: **Client-Server Architecture**.

In this model:
- The **Client** initiates requests. It is typically user-facing (a browser, mobile application, CLI tool, or IoT sensor) and responsible for user interactions and presentation logic.
- The **Server** passively listens on a network interface for incoming connections. It is responsible for authorization, data consistency, business logic execution, and persistence.

<InfoCallout type="note" title="Engineering Invariant">
Clients and servers are roles defined by network behavior, not hardware types. A backend service acting as a server to incoming user requests frequently acts as a client when fetching data from an upstream PostgreSQL database or Redis cluster.
</InfoCallout>

## 3. Why Did Client-Server Win Over Peer-to-Peer?

In the early decades of networking, peer-to-peer (P2P) and mainframe terminal architectures competed for dominance. Client-server architecture prevailed for commercial software engineering due to distinct operational trade-offs:

## 4. The Principle of Statelessness

Modern scalable client-server systems operate under the **Stateless Protocol** invariant. 

A protocol is *stateless* if each individual request from a client to a server contains all the contextual information necessary for the server to understand and authorize the request. The server does not store active session context in its local memory between consecutive requests.

```
┌─────────────────┐                       ┌─────────────────┐
│     Client      │                       │     Server      │
└────────┬────────┘                       └────────┬────────┘
         │                                         │
         │  GET /cart?user=42 (Includes Auth Token)│
         │────────────────────────────────────────►│ Validates Token
         │                                         │ Reads Cart from DB
         │  200 OK [Item 1, Item 2]                │
         │◄────────────────────────────────────────│
         │                                         │ (Server memory cleared)
         │                                         │
         │  POST /checkout (Includes Auth Token)   │ Any server in pool
         │────────────────────────────────────────►│ can handle this!
         │                                         │
```

If Server A crashes between request #1 and request #2, a load balancer can seamlessly route request #2 to Server B without the user noticing any session loss.

## 6. Key Takeaways

1. **Roles, Not Hardware**: Clients initiate connections; servers listen and respond.
2. **Stateless Scalability**: Moving session state into distributed storage (e.g., Redis or database) allows web servers to be spun up or down horizontally on demand.
3. **Connection Lifecycle**: Every HTTP request involves socket allocation, transport handshakes, payload serialization, and socket cleanup.
