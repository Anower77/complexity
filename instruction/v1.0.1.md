# COMPLEXITY — Platform Architecture & Foundation

## 1. Your Role

Act as a Senior Software Architect, Frontend Engineer, UI/UX Designer, Technical Documentation Architect, and Educational Platform Engineer.

You are responsible for building the foundation of a professional engineering education platform named **Complexity**.

Do not treat this as a normal blog or portfolio website.

It should be a structured, course-oriented technical learning platform inspired by the learning experience and information architecture of ByteByteGo.

Reference:
https://bytebytego.com/courses/coding-patterns/two-pointers/introduction-to-two-pointers

Use this reference to understand:
- Course-based learning navigation.
- Chapter and lesson organization.
- Structured lesson reading experiences.
- Persistent course navigation.
- Technical diagrams and illustrations.
- Code examples.
- Lesson progress and completion.
- Previous and next lesson navigation.
- A focused reading environment.

IMPORTANT: Build an original Complexity design and identity. Do not copy ByteByteGo's branding, proprietary illustrations, text, layouts pixel-for-pixel, or other copyrighted material.

# 2. Product Identity

Product name: Complexity

Brand: Complexity

Proposed domain: complexity.github.io

Product category: Interactive Engineering Education Platform.

Core positioning:

"Understand how systems work, why they break, and how engineers design them to scale."

The platform should help developers understand engineering concepts through:
- Visual explanations.
- Structured technical lessons.
- Architecture diagrams.
- Interactive simulations.
- Practical examples.
- Engineering trade-offs.
- Real-world architecture scenarios.

The experience should feel like a professional technical learning product, not a collection of random blog posts.

---

# 3. IMPORTANT DEVELOPMENT SCOPE

This phase is ONLY about building the platform structure and reusable infrastructure.

Do not write the complete educational content yet.

Do not create ten or twenty articles.

Do not populate the platform with extensive networking, Docker, Redis, Kubernetes, or system-design lessons.

Instead, build a fully functional content architecture that will allow these topics to be added later without changing the application's fundamental structure.

Use a small amount of clearly labeled placeholder content to test the system.

The architecture must support future expansion.

---

# 4. Technology Stack

Use the following technologies:

- Astro: Main application framework.
- TypeScript: Strict type safety.
- Tailwind CSS: Styling and design system.
- MDX: Future technical lesson content.
- React: Interactive components only.
- SVG: Custom diagrams and illustrations.
- Mermaid: Simple technical diagrams.
- Recharts: Charts and metric visualizations when needed.
- Motion: Purposeful animations, only where necessary.
- GitHub Actions: CI/CD.
- GitHub Pages: Initial deployment.

Architecture principles:

1. Static-first architecture.
2. Component-driven frontend.
3. Data-driven course navigation.
4. Reusable lesson templates.
5. Strong separation of content and presentation.
6. Minimal JavaScript on pages that do not need interactivity.
7. Accessible and responsive design.
8. No unnecessary backend.

Do not introduce a database, authentication service, API server, or microservices at this stage.

Do not introduce React Flow unless there is a real requirement for interactive node-based editing. Start with reusable SVG-based architecture visualizations.

# 12. Progress Tracking

For the initial static platform, use browser localStorage for lesson completion and reading progress where appropriate.

Requirements:
- Mark a lesson as completed.
- Continue from the last visited lesson.
- Display chapter completion.
- Display course completion.
- Provide a reset option.
- Handle missing or unavailable browser storage gracefully.

Important limitations:
- Progress is local to the browser.
- There is no cross-device synchronization.
- Do not imply that users have accounts.
- Keep progress logic separate so it can later be replaced by an authenticated backend if required.

Avoid collecting personal information.

- Semantic HTML.
- Keyboard-accessible navigation.
- Visible focus states.
- Appropriate contrast.

- Reduced-motion support.
- Responsive reading layout.
- Proper heading hierarchy.

Do not sacrifice accessibility for animation or visual appearance.

# 20. Development Workflow

Work in the following order.

## Step 1 — Repository Inspection

Inspect the existing repository.

Identify:
- Existing code.
- Existing configuration.
- Existing deployment setup.
- Existing assets.
- Existing dependencies.
- Potential conflicts.

Do not overwrite existing working code without understanding it.

## Step 2 — Architecture Proposal

Before implementation, present:
- Proposed architecture.
- Final folder structure.
- Technology decisions.
- Content data model.
- Routing approach.
- Important trade-offs.
- Potential risks.

Keep this proposal concise and technically specific.

## Step 3 — Project Foundation

After the architecture is approved:
- Initialize or configure Astro.
- Configure TypeScript.
- Configure Tailwind.
- Configure MDX.
- Establish design tokens.
- Create the project structure.
- Implement the common layouts.
- Implement the basic navigation.

## Step 4 — Content Engine

Implement:
- Course loading.
- Chapter loading.
- Lesson loading.
- Metadata validation.
- Dynamic route generation.
- Previous and next navigation.
- Table of contents.

## Step 5 — Learning Experience

Implement:
- Homepage.
- Course directory.
- Course overview.
- Lesson reading page.
- Sidebar navigation.
- Mobile navigation.
- Reading progress.
- Local lesson completion.

## Step 6 — Reusable Visualization Foundation

Implement the visualization interfaces and one simple sample visualization to verify embedding and responsive behavior.

Do not build a complete library of simulations.

## Step 7 — Quality Assurance

Run:
- Production build.
- TypeScript checks.
- Tests.
- Accessibility checks.
- Responsive checks.
- Link and route checks.

## Step 8 — Deployment Preparation

Configure GitHub Actions and prepare the Pages deployment.

Verify the deployment before reporting success.

# 21. Engineering Standards

Follow these standards:

1. Use strict TypeScript.
2. Prefer small reusable components.
3. Avoid unnecessary abstractions.
4. Avoid duplicated navigation logic.
5. Keep business logic outside UI components.
6. Keep course data independent of page components.
7. Use Astro components for static UI.
8. Use React only when client-side interaction is required.
9. Avoid unnecessary client-side JavaScript.
10. Do not invent technical claims or production benchmarks.
11. Do not use fake platform statistics.
12. Document architectural decisions.
13. Avoid overengineering.
14. Make every dependency justify its existence.
15. Keep the project easy for another developer to understand and contribute to.
