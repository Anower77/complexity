# COMPLEXITY — Master Project Development&#x20;

## Role

Act as a Senior Software Architect, Frontend Engineer, Technical Educator, UX Designer, and Interactive Visualization Engineer.

You are responsible for designing and developing a professional engineering education platform called **Complexity**.

Website: `complexity.github.io`

The platform teaches software engineering fundamentals, infrastructure, backend technologies, distributed systems, and large-scale system architecture through deeply explained articles, interactive diagrams, realistic engineering scenarios, and simulations.

This is not a traditional blog. It is an interactive engineering learning platform.

## 1. Product vision

Build a platform where a beginner can understand how software systems work, explore their internal components, understand real production problems, and gradually develop the ability to design scalable architectures.

The learning experience must combine:

- Technical storytelling.
- Step-by-step explanations.
- Architecture diagrams.
- Interactive component exploration.
- Dynamic simulations.
- Real-world engineering scenarios.
- Performance and traffic analysis.
- Failure scenarios and engineering trade-offs.
- Knowledge checks.

The platform should explain not only WHAT a technology is, but also:

1. Why does it exist?
2. What problem does it solve?
3. How does it work internally?
4. What happens when it receives traffic?
5. What happens when it fails?
6. What alternatives exist?
7. Why would an engineering team choose it?

## 6. Standard article architecture

Every article must follow a reusable editorial structure.

1. Article introduction.
2. The real engineering problem.
3. Historical or technical background when relevant.
4. Fundamental explanation.
5. Internal working mechanism.
6. Architecture diagram.
7. Component-by-component explanation.
8. Request or data lifecycle.
9. Interactive visualization.
10. Industry use case.
11. Production traffic scenario.
12. Failure scenarios.
13. Bottlenecks.
14. Trade-offs.
15. Alternative technologies.
16. Interview questions.
17. Knowledge check.
18. Further reading.

Use simple language without sacrificing technical accuracy.

Explain new terminology before depending on it.

Do not assume that readers already understand advanced engineering concepts.

## 7. Interactive visualization engine

Develop reusable visualization components.

Required components:

- ArchitectureCanvas
- NetworkDiagram
- DataFlow
- ComponentInspector
- TrafficSimulator
- CacheSimulator
- LoadBalancerSimulator
- DatabaseSimulator
- QueueSimulator

Every architecture diagram should support appropriate interactions:

- Click a component to inspect it.
- Highlight connected components.
- Show incoming and outgoing connections.
- Display request flow.
- Explain the responsibility of each component.
- Switch between architecture states.
- Animate data movement where useful.

Simulations should provide:

- Adjustable inputs.
- Dynamic results.
- Charts or visual indicators.
- Clear explanations of assumptions.
- Reset controls.
- Educational explanations of what changed.

Do not make diagrams decorative. They must help readers understand engineering behavior.

## 8. Initial simulation requirements

Implement these progressively:

### Networking simulator

Show a request moving through:

Client → DNS → Network → Server → Application → Response.

Allow the reader to inspect each stage.

### Docker simulator

Explain:

- Host operating system.
- Container runtime.
- Images.
- Containers.
- Volumes.
- Networks.

Show the relationships between these components.

### Redis simulator

Allow users to change:

- Incoming request rate.
- Cache hit ratio.
- Database baseline capacity.
- Cache availability.

Calculate illustrative cache-hit and database-miss workloads.

### Load balancing simulator

Allow users to:

- Add backend servers.
- Remove backend servers.
- Change incoming traffic.
- Select a distribution strategy.
- Inspect the distribution.
- Explore what happens when a server becomes unavailable.

### Database simulator

Explore:

- Read/write operations.
- Index usage.
- Replication.
- Read replicas.
- Connection pooling.

All simulation calculations must be transparent and explain their assumptions. Never present illustrative simulation values as verified production benchmarks.

## 14. Engineering quality standards

Follow these requirements:

- TypeScript strict mode.
- Reusable components.
- Consistent naming.
- Accessible interactive controls.
- No unnecessary dependencies.
- No duplicated simulation logic.
- No hardcoded article-specific layouts.
- Responsive SVG diagrams.
- Proper error handling.
- Meaningful empty states.
