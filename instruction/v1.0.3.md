# 3. ClusterIP

## Explanation

ClusterIP is the default Kubernetes Service type.

It provides an internal cluster IP through which other workloads inside the cluster can access the Service.

It is not ordinarily exposed directly to external clients on the public internet.

# 4. NodePort

## Explanation

NodePort exposes a Service through a port on each Kubernetes node.

The same configured NodePort is made available on the nodes, subject to the cluster's networking and firewall configuration.

The default NodePort allocation range is 30000–32767.

Explain that a client can reach the Service through:

Node IP + NodePort

Example:

http://NODE_IP:30080

Use a clearly labeled illustrative IP address, not a real production endpoint.

Show that a request arriving at a NodePort can be routed to a Service backend endpoint according to the cluster's Service implementation and configuration.

Important: Do not incorrectly imply that a request arriving at Node 1 must always go to a Pod running on Node 1. Kubernetes Service traffic can be routed to eligible endpoints on other nodes, depending on configuration.

# 5. LoadBalancer

## Explanation

LoadBalancer requests an external load-balancing entry point for a Service.

In supported cloud environments, Kubernetes integrates with the infrastructure provider or load-balancer implementation to provision and configure the external load balancer.

A client can then access the Service through the external load-balancer address.

Explain that the exact implementation and traffic path depend on the cloud provider, Kubernetes networking implementation, and configuration.

Do not imply every LoadBalancer Service always works identically.

Explain that implementations can differ:

- Some environments route traffic through NodePorts.
- Other implementations can route directly to Pods or use different datapaths.
- Some implementations may allocate NodePorts by default, while others can be configured differently.

Do not present the illustrative diagram as the only possible production implementation.

# 11. Common misconceptions and failure scenarios

Add a troubleshooting section.

Explain:

1. ClusterIP is not a public IP.
2. NodePort does not automatically create a cloud load balancer.
3. LoadBalancer does not guarantee a public IP in every environment.
4. A Service selector must match the intended Pod labels.
5. A Service port and container targetPort are different concepts.
6. A Pod can be running while the application is not accepting connections.
7. Network policies and firewall rules can affect reachability.
8. Actual traffic paths vary across implementations.

- State the incorrect assumption.
- Explain the correct behavior.
