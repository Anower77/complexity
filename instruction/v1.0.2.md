# 4. Professional visual identity

The current visual presentation needs a serious redesign.

The color system, contrast, alignment, spacing, and content presentation must look professional and consistent.

Do not randomly select colors for individual sections.

Create a complete design system first.

## 4.1 Color direction

Use a restrained, engineering-focused visual identity.

Suggested palette:

### Light theme

- Main background: #F8FAFC
- Primary surface: #FFFFFF
- Secondary surface: #F1F5F9
- Primary text: #172033
- Secondary text: #64748B
- Border: #E2E8F0
- Primary accent: #315E8A
- Secondary accent: #397C78
- Highlight: #EAF1F8

### Dark theme

- Main background: #10151D
- Primary surface: #171F2B
- Secondary surface: #1E2938
- Primary text: #E7EDF5
- Secondary text: #A3B0C2
- Border: #2B394A
- Primary accent: #83ADD6
- Secondary accent: #75B6A9
- Highlight: #22364A

These are starting tokens, not permission to use every color everywhere.

Use:
- Neutral backgrounds.
- Restrained accent colors.
- Subtle borders.
- Consistent surface hierarchy.
- Clear typography.
- Small amounts of color for meaningful states.

Avoid:
- Excessive gradients.
- Neon colors.
- Random purple-blue combinations.
- Excessive glassmorphism.
- Colorful cards everywhere.
- Too many accent colors.
- Low-contrast text.
- Unnecessary shadows.
- Different colors for unrelated sections.

Use color to communicate information, not decorate empty space.

All colors must work in both light and dark modes.

## 4.2 Typography

Establish a professional typography system.

Suggested:
- Inter or another readable sans-serif for UI and body text.
- A carefully selected editorial font for large headings if needed.
- JetBrains Mono for code and technical identifiers.

Typography requirements:
- Strong heading hierarchy.
- Readable paragraph width.
- Consistent line height.
- Proper spacing between headings and content.
- Comfortable technical article reading.
- Distinct code typography.
- Responsive font sizing.

Avoid oversized headings and excessively small descriptions.

## 4.3 Layout and alignment

Every page must follow a consistent spacing and alignment system.

Define:
- Maximum page width.
- Main content width.
- Header height.
- Sidebar width.
- Article width.
- Section spacing.
- Card padding.
- Grid gaps.
- Responsive breakpoints.

Ensure:
- Elements align to a consistent grid.
- Cards have consistent heights where appropriate.
- Headings align with their content.
- Buttons have consistent dimensions.
- Sections have deliberate spacing.
- Navigation does not overlap content.
- Mobile layouts do not overflow horizontally.

Do not fix alignment issues using arbitrary margins and one-off CSS hacks.

Use reusable layout primitives and design tokens.

# 7. Dynamic Learning Path and Knowledge Graph

This is a high-priority feature.

Create a reusable interactive knowledge graph.

The graph must represent actual topic relationships.

## Data model

Each topic node should support:

- id
- slug
- title
- shortDescription
- category
- difficulty
- prerequisites
- relatedTopics
- nextTopics
- articleReferences
- status

Each connection should support:

- source
- target
- relationshipType
- description
- order
- optionalLabel

Relationship types should include:

- prerequisite
- builds-on
- related-to
- alternative-to
- commonly-used-with

Do not treat every connection as a strict prerequisite.

## Graph functionality

The interactive graph must support:

1. Click a node.
2. Display a topic detail panel.
3. Highlight connected topics.
4. Highlight prerequisites.
5. Highlight recommended next topics.
6. Show the learning sequence.
7. Open the corresponding article.
8. Filter by topic category.
9. Search topics.
10. Reset the current selection.
11. Zoom and pan.
12. Keyboard-accessible navigation.

## Learning path logic

A user should be able to understand:

- What should I learn first?
- Why should I learn it?
- What concepts depend on it?
- What should I learn next?
- Which topics are optional?
- Which topics are related but not prerequisites?

For example:

Networking fundamentals should lead towards:
- DNS.
- TCP/IP.
- HTTP/HTTPS.
- Reverse proxies.
- Load balancing.

HTTP/HTTPS should connect to:
- REST APIs.
- TLS.
- Backend request lifecycle.
- API gateways.

Database fundamentals should connect to:
- Indexing.
- Transactions.
- Connection pooling.
- Replication.
- Sharding.

Caching should connect to:
- Redis.
- Cache invalidation.
- Cache-aside.
- Write-through.
- Cache stampede.

The relationships must be technically meaningful.

Do not force every topic into one linear sequence.

## Visual implementation

Use SVG as the initial rendering technology.

Use React for graph interactions if required.

Only introduce React Flow or another graph library if the implementation genuinely needs it.

Do not add a large graph dependency for a simple static diagram.

Graph requirements:
- Smooth but restrained transitions.
- Clear node states.
- Readable labels.
- Visible edge relationships.
- Consistent category styling.
- Responsive behavior.
- Reduced-motion support.
- Accessible non-graph alternative.

## Diagram types

### A. Architecture diagrams

Examples:
- Client-server.
- Three-tier architecture.
- Monolith.
- Microservices.
- Event-driven architecture.

### B. Request flow diagrams

Examples:
- Browser to server.
- DNS resolution.
- HTTPS handshake at a conceptual level.
- API request lifecycle.
- Reverse proxy routing.

### C. Data flow diagrams

Examples:
- Cache read and miss.
- Database write.
- Message producer and consumer.
- Replication flow.

### D. Infrastructure diagrams

Examples:
- Docker host and containers.
- Nginx reverse proxy.
- Load balancer and backend instances.
- Kubernetes conceptual architecture.

### E. Sequence diagrams

Examples:
- Login request.
- API authentication.
- Background job execution.
- Notification delivery.

## Interactive features

Where useful:
- Click components to inspect them.
- Highlight the selected flow.
- Animate data movement.
- Show request sequence numbers.
- Display component descriptions.
- Explain what happens at each stage.
- Allow users to switch architecture states.
- Compare before and after architecture.

Example:

Single Server
    |
    v
Traffic increases
    |
    v
Server reaches capacity
    |
    v
Add Load Balancer
    |
    +--------+--------+
    |        |        |
 Server A Server B Server C

The visualization should explain why the architecture changed and what new problems appeared.

## Diagram design rules

- Use consistent node shapes.
- Use consistent connection styles.
- Use meaningful labels.
- Avoid excessive colors.
- Keep text readable.
- Use arrow directions correctly.
- Explain assumptions.
- Include captions and accessible descriptions.
- Ensure diagrams work in dark and light themes.

Do not animate everything.

Animation must communicate direction, sequence, state changes, or causality.

# 12. Recommended technical stack

Keep the architecture simple.

- Astro: Static-first application.
- TypeScript: Strict typing.
- Tailwind CSS: Styling.
- MDX: Articles.
- React: Interactive diagrams and simulations only.
- SVG: Diagram rendering.
- Mermaid: Simple diagrams when appropriate.
- Recharts: Only when a real chart is needed.
- Motion: Only for meaningful transitions.
- GitHub Actions: Deployment.
- GitHub Pages: Hosting.

Do not install every library immediately.

Before adding a dependency, explain:
- What problem it solves.
- Why existing technologies cannot solve it.
- Its impact on bundle size.
- Whether it needs client-side JavaScript.

Do not introduce:
- A backend.
- A database.
- Authentication.
- Payment integration.
- Course enrollment.
- Subscription functionality.

# 20. Final instructions

Do not interpret this task as "change the colors and add animations."

The goal is to transform Complexity into a coherent engineering knowledge publication.

The platform should make visitors understand:

1. What engineering concept they are looking at.
2. Why it matters.
3. How it works.
4. Which components it connects to.
5. What they should learn before it.
6. What they should learn next.
7. How the concept appears in real system architecture.

The most important differentiator should be the relationship between technical articles, learning paths, and interactive architecture diagrams.

Prioritize clarity over decoration.

- Existing issues identified.
- Design changes made.
- Components created or modified.
- Architecture changes.
- Dependencies added or removed.
