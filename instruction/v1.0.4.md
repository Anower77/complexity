# 9. INTERACTIVE ARCHITECTURE DIAGRAM ENGINE

This is one of the most important features of Complexity.

Build a reusable diagram engine that can be embedded inside any article.

The diagram engine must support:

- Architecture diagrams.
- Network diagrams.
- Request flow diagrams.
- Data flow diagrams.
- Sequence diagrams.
- Infrastructure diagrams.
- Deployment diagrams.
- Database relationship diagrams.

## Diagram components

Create reusable visual primitives:

- ClientNode.
- ServerNode.
- DatabaseNode.
- CacheNode.
- QueueNode.
- GatewayNode.
- LoadBalancerNode.
- ContainerNode.
- PodNode.
- NetworkBoundary.
- ConnectionLine.
- DirectionalArrow.
- Annotation.
- GroupContainer.

These components should have consistent styling.

## Diagram interactions

Support:

- Component selection.
- Component inspection.
- Connection highlighting.
- Request flow highlighting.
- Data flow highlighting.
- Expand and collapse.
- Zoom.
- Pan.
- Reset.
- Step-by-step execution.
- Optional architecture state switching.

Do not create an enormous diagram component.

Separate diagram data, rendering, animation and interaction logic.

## Animation requirements

Animations should explain system behavior.

Examples:

- A request travels from client to server.
- A database query travels through an application.
- A cache hit returns data without reaching the database.
- A cache miss reaches the database.
- A load balancer distributes incoming requests.
- A message queue receives and delivers messages.
- Replication moves data between database instances.

Each animation should represent a meaningful state transition.

Do not add random moving dots or continuous decorative motion.

Every animated flow must explain:

1. What is moving?
2. Where does it start?
3. Where does it go?
4. Why does it move?
5. What changes when it reaches the destination?

Support:

- Play.
- Pause.
- Reset.
- Next step.
- Previous step.
- Reduced-motion mode.

Animations must never be the only way to understand the explanation.
